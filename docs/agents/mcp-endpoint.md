# The MCP endpoint at `/mcp` (fork only)

pi-web's own MCP server, for agents that work in pi sessions beside a person in the browser. Not to be confused with pi-web as an MCP *client* (`lib/mcp-*.ts`, `app/api/mcp/`, Settings › MCP): that code is unrelated, which is why this module is `lib/mcp-endpoint/`, never `lib/mcp-server*`, and why its types avoid the client's names (`EndpointServer`, not `McpServerDefinition`). User doc: [docs/mcp-endpoint.md](../mcp-endpoint.md).

## Shape and ownership
- A call goes `app/mcp/route.ts` → `handleMcpBody()` in `jsonrpc.ts` → a tool's `run` in `tools.ts` → one `Desk` method in `desk.ts`, and the reply text comes from `replies.ts`. Each file owns one layer: HTTP (`http.ts`), protocol (`jsonrpc.ts`), tool specs and instructions (`tools.ts`), every reply the agent reads (`replies.ts`), runtime (`desk.ts`). `transcript.ts` (cursor, delta, authors), `rest.ts`, `session-ledger.ts` and `process-global.ts` are pure and sit beside that path.
- **`ports.ts` is the only file that imports pi-web's runtime**: the wrappers (`rpc-manager`), session files (`session-reader`, `session-family`), git (`worktree`), liveness (`session-liveness`), subagents (`subagent-runtime`), trust (`project-trust`), file access (`file-access`), the directory picker's resolution (`directory-browser`), terminals (`terminal-manager`, `terminal-list`), and `extension-ui-queue`, `tool-presets`. The one other runtime import is `@xterm/xterm` in `terminal-render.ts`. The other files import only leaf helpers and types. `http.ts` and the route import `request-security`. `desk.ts` imports `message-display`, `path-security`, `session-ui-state-shared` and `tool-fields`. `replies.ts` imports `session-links`, and `tools.ts` imports `tool-presets` and `package.json`. `desk.ts`, `replies.ts` and `transcript.ts` import `types`.
- `desk.ts` is written against `PiWebPorts` / `LiveSession`, never the runtime itself. `ports.integration.test.mjs` pins the upstream behavior the interface promises, on a real wrapper with pi-ai's faux provider. After a rebase, a reshaped runtime API breaks `tsc` in `ports.ts` or that test; a reshaped leaf helper breaks `tsc` where it is imported.
- **`ports.listSessions()` copies the join in `app/api/sessions/route.ts`** (saved rows, live-only rows, merge, running and awaiting-input ids) on purpose: extracting it would edit an upstream route. When a rebase changes that route's join, mirror the change here.
- **Upstream files change in three places.** One is the pointer line in AGENTS.md. Another is `hooks/useAgentSession.ts`: the `Fork:` block in `handleSend`, its `isAgentBusyRefusal` import, and the `sendStreamingPromptRef` ref (declared beside `handleNavigateRef`, assigned after `sendStreamingPrompt`). Each is an inserted line; no upstream line changes. The third is `handleOpenTerminal` in `components/AppShell.tsx` and its `terminalTabFor` import (see Workspace terminals). `proxy.ts`, `instrumentation-node.ts` and `package.json` stay untouched: there is no MCP SDK dependency (a lockfile diff on every rebase), and the protocol slice is hand-written. `lib/agent-busy-refusal.ts` and the tests are new fork-only files.
- Process-wide state goes through `processGlobal()` (`process-global.ts`), under `Symbol.for("pi-web.mcp-endpoint.<name>")`. That holds the desk's memory (`DeskMemory`: the ledger, the holds, the checkouts under way), the terminal desk's memory (`terminal-desk`), the shutdown controller, and the short-token warning. Route bundles and dev hot reloads each evaluate the modules again. A reload builds a new desk around the same memory, so its rules stay in `desk.ts` and its state survives.

## Guard (`http.ts`)
- `proxy.ts`'s matcher (`/`, `/login`, `/api/:path*`) does not cover `/mcp`, so the route guards itself, as `app/api/web-auth/route.ts` does. Order: no usable `PI_WEB_MCP_TOKEN` (unset, or under 32 characters after trimming) → 404 for every method; `isApiRequestAllowed()` (Host allow-list, cross-site Origin / Fetch Metadata) → 403; bearer mismatch → 401 with `WWW-Authenticate: Bearer realm="pi-web", error="invalid_token"`. Off is 404, not 401: a 401 sends some clients into OAuth discovery.
- The bearer is compared as sha256 digests with `timingSafeEqual`, read from the env on every request. **Never feed `lib/auth-throttle.ts`**: its backoff is global and shared with the login form, so a token prober would lock the person out of the web UI.
- Do not move the guard into `proxy.ts`: matching `/mcp` there makes Next tee and buffer the body for the proxy, and Basic auth is read only for `/api`.
- Links in replies use `PI_WEB_MCP_LINK_BASE`, else the request's `Host` and first `x-forwarded-proto`. Never `request.url`: under `next start` it can hold the bind address. `guardMcpRequest()` refuses a request without `Host` and hands the allowed one's `Host` to `linkBaseFor()`.

## Protocol slice (`jsonrpc.ts`)
- Streamable HTTP in JSON response mode only. Every POST gets one `application/json` body (an array for a 2025-03-26 batch), or 202 when no message needs an answer. No `Mcp-Session-Id`, no SSE. GET and DELETE answer 405 with `Allow: POST` and -32000 (`RPC.serverError`). Nothing is ever a stream, so compression, proxy buffering and shutdown need nothing special.
- `handleMcpBody()` runs the whole pipeline from the body's text: parse, check the version header, answer each message, choose 200, 400 or 202. The route keeps only the guard, the content type, the 1 MiB body limit and that one call.
- `MCP-Protocol-Version`: absent means 2025-03-26. A version outside `PROTOCOL_VERSIONS` is a 400 with the request id echoed, except for a body of `initialize` requests only, which negotiates in its params. Claude Code's first probe is `server/discover` under a newer revision; the 400 is its signal to fall back to `initialize`. Without the header the probe gets -32601.
- A message whose `jsonrpc` member is not `"2.0"` is invalid (-32600). `answer()` switches on the four methods (`initialize`, `ping`, `tools/list`, `tools/call`); any other is -32601. `initialize` inside a batch is -32600. `notifications/cancelled` is ignored: a client that gives up drops the HTTP request, which aborts the call's signal.
- A tool's input schema is a JSON Schema subset (`ArgSchema`). `tools/list` publishes it as written, `validateArgs()` enforces it exactly as published (`minLength` counts characters, untrimmed), and `ArgsOf<S>` derives `run`'s argument type from it. Bad arguments are an `isError` result the model reads, not a protocol error.
- Tools never catch. `callTool()` alone sorts a throw: an error `EndpointServer.isToolError()` accepts (in pi-web, a `ToolError`) is answered with its message as an `isError` result; any other throw is logged and answered `pi-web failed: …`.
- A schema uses only keywords `validateArgs()` enforces, and every `pi_*` name in the instructions, descriptions and reply text is a tool.

## Bounds and shutdown
- No call runs past 50 s (`WAIT_MAX_MS`): Claude Code allows about 60 s to a response's first byte, as do the generic MCP SDK client and nginx's default; Cloudflare's 524 comes at 100 s. `pi_send` waits up to 15 s for pi to take a message (`SEND_ACCEPT_MS`), `pi_new_session` 30 s for the build plus those 15 s, `pi_new_worktree` 45 s, `pi_stop` 5 s for the agent's own send on its way plus 20 s for the run to unwind. Past a bound the reply says what is still under way; nothing is cancelled.
- `shutdownSignal()` registers its own once-per-process SIGTERM/SIGINT listener (no `instrumentation-node.ts` edit; that file already listens, so the extra listener changes no exit behavior). Every call's signal is `AbortSignal.any([request.signal, shutdownSignal()])`, so a pending `pi_wait` answers at once when `next start` closes the server (`app/mcp/route-shutdown.integration.test.mjs`).

## Sending (`desk.ts` `deliver()`)
- **Every prompt carries `streamingBehavior`** (`followUp`, or `steer` on request): `LiveSession.prompt()` cannot express a plain prompt. With it, `send({type:"prompt"})` atomically starts a run on an idle session or queues into anyone's run, so the agent never gets "Agent is already processing". Never use the `steer` / `follow_up` commands: they skip admission, the MCP wait and the cwd check, and can strand a message in an idle queue.
- `send()` resolves at acceptance, not at the end of the run, and waits for extensions to bind first (a `session_start` dialog can hold it). The prompt is never tied to the call's signal: once handed to pi-web it is pi's, and a cancelled call can still deliver.
- "started" or "queued" in the reply is a guess from `isRunning()` before the send: `wrapper.send()` drops the SDK's preflight disposition.
- A send with no cursor returns one at the leaf before it, with `dialogs: "0"`, so the next wait shows the message landing and any dialog already open.
- A blank message is refused before a session is touched or made (`refuseBlank()`): pi would hand it to the model as it is.

## The cursor and the delta (`transcript.ts`)
- The agent's whole read state is `{entryId, dialogs, at}`, encoded `<entryId|->~<digest>~<at base36>`. The server keeps nothing per agent: a lost reply is repeated with the same cursor, and entry ids survive restarts and wrapper replacement.
- `branchSince()` walks from the leaf up to the cursor's entry through `getEntry()`: `since` (an ancestor), `moved` (another branch, after "Edit from here" or a branch switch; entries from the deepest common ancestor) or `unknown` (not in this session; the newest entries). It is capped to `MAX_DELTA_ENTRIES`.
- The agent sees what the chat shows. `shownMessages()` in `desk.ts` converts the entries and drops what upstream's `isHiddenCustomMessage()` hides, and a wait has news only when something is left. A background `session_info` title write converts to no message, so it wakes no waiter; a `display: false` custom message never reaches the agent.
- Slices convert with `buildSessionContext(slice, slice.at(-1).id)`: the branch walk stops where a parent is missing, so it converts exactly the slice.
- `authorOf()` names who wrote a user message (the ledger knows) and marks summary entries. Other messages get `"by-role"`: their role says who, and `replies.ts` labels them `[pi]`, `[shell]` or `[extension …]`.

## When a wait is over (`rest.ts`)
- **Never `prompt_done`**: pi-web emits it only for prompts without `streamingBehavior`, never for runs the person or a subagent report started, and for a deferred prompt before its run begins.
- pi's SDK clears its run flag before it awaits extensions' `agent_settled` handlers, and a prompt arriving then starts its run right after the emit. So rest is not busy, with something new, continuously for `SETTLE_MS` (600 ms). `isBusy()` is the busy rule: `isRunning()`, an unsettled subagent run, or the agent's own send still on its way. The timeout reply's "still working" uses the same function. A new `agent_start` while settling drops back to watching.
- An open blocking dialog whose ids digest differs from the cursor's ends the wait (`unseenDialog`). One the agent was already shown does not, so an agent that leaves a dialog to the person is not woken by it again.
- On an idle session with nothing new, a wait waits for the person until its deadline. A timeout still carries the progress and a new cursor, so the agent can steer mid-run.

## Watching a session (`SessionWatch` in `desk.ts`)
- Reads and waits **never start a wrapper**, and never read with `force`, which can evict an idle wrapper. With no live wrapper a wait ticks every second and attaches when the person's page starts one.
- `onEvent()` replays the wrapper's state synchronously inside the call: open dialogs, each running top-level tool's start and latest update, and the startup notices. The watch ignores the replay, because it is state, not news. `openDialogs()` and `runningTools()` read a fresh replay on every check, so a wait and a read name the same dialogs and the same running tool. A `session_ended` in the replay (a wrapper an extension shut down) detaches without waking; waking on it re-attached to the ended wrapper in a loop that never yielded.
- `session_shutdown` and `session_ended` detach. The next observation re-resolves through `getRpcSession()`, which finds whatever replaced the wrapper (fork, trust change, idle reap, a tool switch across Chat only). Never call `wrapper.onDestroy()`: the registry owns that single callback.
- `message_update`, `tool_execution_update` and `bash_output` do not wake a waiter; every other event does. `ports.ts` narrows the wrapper's events into `SessionEvent`.

## The sent-message ledger (`session-ledger.ts`)
- The only memory about sends, kept in `DeskMemory`. Per pi session (there is no agent identity), it holds the endpoint's sends. Each has an outcome (`sending` → `accepted` | `parked` | `refused`) and a placement (`open` → `landed` on an entry, or `missing` since a time). Each is set once, so concurrent waits may all `observe()` the ledger. At most 200 per session, none older than 24 h, lost on restart.
- The ledger owns a send's lifecycle: `observe()` lands sends and finds missing ones, `withdraw()` labels what Stop withdrew, `authorOf()` labels user entries, `deliveryNewsSince()` and `inFlight()` answer the desk.
- **Labels**: pi records no author. A user entry a send landed on is `[agent]`; an unmatched one newer than the ledger is `[person]`, an older one `[user]`. Landing is a text match: the same trimmed text, and an entry time no earlier than 2 s before the send. Each entry lands one send at most. pi-web must not add an author field to the transcript or the extension API (AGENTS.md's extension-compatibility principle).
- **Delivery news**: a refusal after `pi_send` already replied, or an accepted send that left pi's queue without landing (Stop, or Recall in pi-web), is reported to every cursor older than the event. Missing needs pi at rest, the text out of `queued()`, an age over 2 s, and no leading `/`: an extension command may run without writing a user entry. A send found missing is never matched again; a later entry with its text is the person's.

## Keeping sessions loaded (`hold()` in `desk.ts`)
- Send, wait, answer, stop and create hold the session. Each session id gets one session-liveness provider through `ports.registerLiveness()` (`pi-web-mcp-endpoint`, active for 30 min after the last touch), and the next touch sweeps expired holds. A provider, not `renewIdleTimer()`: it spans gaps longer than the 10-minute idle timeout, follows the session id across wrapper replacement, still yields to Stop's forced shutdown, and shows by name in the Debug panel. Its `isActive()` never throws (a throwing provider pins the session).
- The holds live in `DeskMemory`, so a desk rebuilt after a dev hot reload keeps them and registers no second provider.

## Sessions, worktrees, Stop, dialogs
- `directoryOf()` in `desk.ts` makes every folder argument canonical through `ports.directory()`, as the directory picker resolves it: absolute or `~/…`, `~` expanded, an existing directory, by its realpath. A relative path never reaches the filesystem. So the agent's sessions group with the person's. Any directory is allowed: the token is as strong as the web password.
- `pi_new_session` then does what `/api/agent/new` does (`ports.create()`: a `__new__<uuid>` start key, `allowFileRoot()`, `invalidateSessionListCache()`) and sends the required first message, so every created session is saved and listed. `tools` maps through `getToolNamesForPreset()`; `configured` sends no `toolNames`. Trust stays a human action: the reply only says when project extensions are off.
- `pi_new_worktree` joins a checkout already under way, keyed by the repo's main checkout (`ports.project(dir).mainCheckout`, the same for each of its worktrees) and the trimmed branch, in `DeskMemory.checkouts`. A repeat during a long checkout must not read git's half-made worktree as "exists". A repeat after it lands in `WorktreeBranchInUseError`, answered as "exists". `ports.addWorktree()` only translates upstream's result or error.
- `pi_stop` first gives the agent's own send on its way up to 5 s to land, before it resolves the wrapper: an abort before that prompt would stop nothing, and the prompt would then run. It sends `abort` only when a live wrapper is running or holds a dialog. The withdrawn texts go to the agent, labeled from the ledger, and the agent's own are marked missing.
- `pi_answer` checks the dialog is still open (through the replay), maps the answer to its kind, and sends `extension_ui_response`. The first answer from any client wins; a `custom` panel takes keystrokes and stays the person's.

## Workspace terminals (`terminal-*.ts`)
Six tools share a workspace terminal (a node-pty shell from `lib/terminal-manager.ts`, TM below) with the person's terminal tab. `tools.ts` serves them from `terminal-tools.ts`; `terminal-desk.ts` runs them, `terminal-replies.ts` writes every reply, and `terminal-stream.ts`, `terminal-rest.ts` and `terminal-keys.ts` are pure.
- **Shapes.** `lib/terminal-list.ts` is the only reader of TM's registry outside TM. It reads `globalThis.__piWebTerminals` as `getTerminalStats()` does, never through `registry()`, which would create the map and install the signal handlers. A `TerminalSnapshot` (id, cwd, pid, cols, rows, offset, backlog, state, listeners) is built for each call and never kept. `TerminalPorts` in `ports.ts` adds `start` (`createTerminal(cwd, 120, 40, randomBytes(16) hex)`, then `allowFileRoot(cwd)` so the person's tab passes the allow-list), `hold`, `write`, `close`, `foreground`, `realpath` and `directory`. A `TerminalId` is 32 lowercase hex, the only form a tab adopts.
- **No read state per agent.** The cursor is TM's output offset, `term~<first 8 hex of the id>~<offset base36>`. Every view renders from TM's backlog during the call, so a repeated call with the same cursor gives the same page. A malformed cursor or a session cursor is a `ToolError`. Another terminal's tag, or an offset past the terminal's, is `foreign`: the reply shows the latest view and a fresh cursor. A cursor below the backlog window counts the lost units exactly and continues from the window's start.
- **Rendering** (`renderSpan` in `terminal-render.ts`). One transient `@xterm/xterm` `Terminal` per call, at the PTY's size. It is never `open()`ed and its `onData` is never wired, so it answers no terminal query. It reads the backlog from `windowStart()` (a window that lost its beginning starts after its first line break) up to `from`, puts a marker on each screen row down to the start of the cursor's logical line, then reads on to `to`. The news is the logical lines (wrapped rows joined by `isWrapped`, trailing blanks trimmed) from the checkpoint to the end. It starts earlier at the first row above that a cursor-up redraw changed or erased, and leaves out the cursor's line when that line is unchanged. xterm moves markers as a full buffer drops rows and disposes a marker when its row is erased, so any marker left locates the others; with none left, `trimmed` reports that `clear` erased the checkpoint. While the alternate screen shows, the normal buffer stands still, so a checkpoint taken then waits for the screen's exit sequence. An alternate screen active at `to` comes back as rows and a cursor. The scrollback is sized to the rows the span can add, so a render never allocates rows for the whole 128K window. The desk takes `RenderSpan` as an argument, so `app/api/terminals/route.ts`, which imports the desk for `agentTerminalIds()`, does not pull xterm into its route.
- **An xterm behavior.** A line feed clears the wrap flag of the row it moves to. readline moves down with a line feed when it edits a command across its wrap, so that command reads as two lines. The person's xterm shows the same two rows.
- **Pages** (`pageEnd`, `pageStart` in `terminal-stream.ts`) end at raw line breaks. A page costs one per unit plus one per line break, for the reply's `| `, within `BUDGETS.report.total` (12000) for open, send and wait, and `BUDGETS.read.total` (40000) for read. A single longer line is taken whole and the reply clips it: the render shows whole logical lines, so a cut inside one would show it again on the next page. Output with no line break left is taken to the end.
- **When a wait ends** (`stepTerminalWait` in `terminal-rest.ts`). The desk observes on each hold signal and every 250 ms, for at most 50 s, with cheap raw checks; it renders once at the end. In order: the call aborted, the shell exited or was closed, more news than one page (at once), a line went in and a line editor is quiet 300 ms (`ready`), a line went in and a program is quiet 2 s after output that ends in text or on an alternate screen, or with no front known (`paused`), the deadline. A line went in (`entered`) on a line break, a `?2004h`, an alternate-screen toggle, or an agent input after the cursor. Any other change is `typing`, the person editing a line, and never ends a wait. Quiet counts from the later of the last output and the agent's last input, so a send never reads `ready` before its echo.
- **The front.** bash 5 and Python's REPL turn bracketed paste (`?2004`) on while they read a line and off on Enter (`modesOf`). On with no alternate screen is a line editor. With no toggle in the window, the Linux foreground stands in: `/proc/<shell pid>/stat` field tpgid, then `/proc/<tpgid>/comm`, or a group member's name when a pipeline's leader already exited. Never `pty.process`: it names a pipeline's first command.
- **Sending** (`encodeInput` in `terminal-keys.ts`). Keys, then text, then Enter go out as one write, so the person's keys never land inside them. Arrows and Home/End follow `?1` through `terminalExtraKeySequence`; `ctrl+` and `alt+` go through `applyTerminalModifiers`. Text turns `\r?\n` into `\r`, and multi-line text goes through `asBracketedPaste` when `?2004` is on, as the person's paste does. Ctrl+C, Ctrl+Z and Ctrl+\ must come alone: the line discipline drops input typed ahead of a signal. With text and a cursor, the desk refuses `already-typed` (an agent input at or after the cursor: a retried call), `changed` (since the cursor a line went in, or the cursor's line, its column or a full screen reads differently: the person may be typing) or `foreign`. `changedSince` renders both ends; the render's `input` is the cursor's logical line and column. A redraw alone, such as the shell drawing its line again when the person's tab joins or resizes the terminal, changes none of that, so the agent types. Keys or Enter alone are never refused. The reply then waits from the cursor, or without one from the offset before the write, so no output before the agent's input is skipped.
- **Holds.** `open`, `send` and `wait` touch the terminal. The first touch subscribes an in-process TM listener (`ports.hold`), which disarms TM's 120 s cleanup; each touch re-arms an unref'd `HOLD_MS` (30 min) timer whose expiry unsubscribes, after which TM's own cleanup applies. `read` and `pi_terminals` hold nothing. The listener is old code after a hot reload, so it only sets `lastOutputAt`, pokes the waits in progress, and on `exit` or `closed` records a tombstone and releases, all inside `try`: a throw would skip TM's later listeners (TM's `emit` has no `try`). The Debug panel counts a hold as one terminal stream.
- **Memory** is `processGlobal("terminal-desk")`, a name of its own: a field added to `DeskMemory` would be missing after a hot reload. It holds the holds (with the agent's last 50 inputs each, for attribution and the send guard), `started` (pruned once TM drops the terminal) and `ended` (terminals that ended while held or that the agent closed: at most 100, each for 1 h). A reply about an ended terminal says who ended it and lists the folder's running terminals, so the agent finds the shell after the person's Restart.
- **Joining.** `pi_terminal_open` joins the folder's running terminal by real path: one a pi-web tab streams first, then the one an agent touched last, then the newest. Only with none does it start a shell, and then it waits (the wait rule, with the shell's first output counting as a line that went in, at most `START_WAIT_MS`, 10 s) until the shell reads its first line. A started shell has printed nothing yet, so a cursor taken at once would sit before its prompt, and the agent's first send would read that prompt as the person typing and type nothing. In the browser, `GET /api/terminals?cwd=` (behind `proxy.ts`) lists the running terminals that an agent started or holds (`agentTerminalIds()`) whose real path equals that of `cwd`, where `cwd` passes `isExistingFilePathAllowed()`, newest agent touch first. `joinableTerminalTab()` (`lib/terminal-join-client.ts`) makes the first a `{ id, cwd, restored: true }` tab with the browser's own `cwd` string, so the one-tab-per-folder match keeps working. `terminalTabFor(cwd)` returns that tab or `newTerminalTab(cwd)`, and calls for one folder while its lookup runs share it: a double click across the lookup resolves both clicks to one tab, so the append's id check keeps one, as upstream's synchronous handler did. A settled lookup is not reused, so the next click asks again. A restored tab GETs and streams, never POSTs a replacement shell (TerminalPanel.tsx), then posts its own size: the person's view owns the size, and the agent never resizes.
- **The upstream edit.** `handleOpenTerminal` in `components/AppShell.tsx` is `async` and takes its tab from `terminalTabFor(cwd)`; the append skips an id already in the list (a double click across the `await`). Marked `Fork:`, with the import beside `terminal-tab-state`. A person's own terminals are never listed, so a person with no agent keeps upstream's behavior, and two browser windows still get a shell each.

## Known limits
- Terminals: output past TM's 131072-unit backlog between two agent calls is lost to the agent, counted exactly. A full-screen program that started before the window renders partially; `ctrl+l` redraws most. The browser's replay has the same limit.
- Terminals: the person's Close or Restart ends the shell for the agent too; the next reply says so and names the folder's running terminals.
- Terminals: two browsers of different sizes still overwrite each other's size, as upstream. A restored tab that was never visible posts xterm's 80x24 on stream open (TerminalPanel.tsx), a base issue.
- Terminals: every shell's environment carries `PI_WEB_MCP_TOKEN`, because TM strips only `PI_WEB_PASSWORD`. That predates the terminal tools; stripping it is one changed upstream line in TM, and pi's own bash tool inherits the token too.
- Terminals: on Windows and macOS there is no foreground, so a wait that never sees a `?2004` toggle ends on quiet periods alone.
- The person's page can send a plain prompt in the moment before it hears of the agent's `agent_start`, and pi refuses it with "Agent is already processing". The `Fork:` block in `handleSend` (`hooks/useAgentSession.ts`) resends the text once as a follow-up, through `sendStreamingPrompt`, so the unconfirmed-send handling of #1432 applies to it. An edit keeps the refusal, since it must branch. `isAgentBusyRefusal()` in `lib/agent-busy-refusal.ts` matches the start of pi's message. `lib/agent-busy-refusal.integration.test.mjs` gets that refusal from a real wrapper and fails when pi rewords it.
- On that lost race, pi runs the extensions' `input` handlers twice for the person's text: once for the refused prompt and once for the follow-up. pi runs them before its busy check (`_preparePrompt()` in pi's `dist/core/agent-session.js`). An upstream pi-web change would remove this and the `Fork:` block. `wrapper.send()` would return pi's preflight answer (started, queued or handled), and pi-web would emit `prompt_done` for every prompt that started a run, not only for those without `streamingBehavior`. `handleSend` could then always send `streamingBehavior: "followUp"`. The `Fork:` block, its tests and the desk's started-or-queued guess would go.
- `queued()` reads the SDK queue only, not prompts parked behind a manual compaction; a parked send's outcome is `parked`, never missing.
- Internal behavior this depends on that no upstream test pins for it: the open dialogs and running tool starts in the `onEvent()` replay, the `abort` reply shape, `inner.getSteeringMessages()` / `getFollowUpMessages()`, and `buildSessionContext()`'s slice walk, each covered by `ports.integration.test.mjs`; pi's busy refusal, covered by `lib/agent-busy-refusal.integration.test.mjs`.
